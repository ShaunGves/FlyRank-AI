AI Referral Opportunity: Which Content Patterns Correlate with AI‑Referred Search Traffic?

By Shaun Gonsalves  ·  Repository: github.com/ShaunGves/FlyRank-AI
Abstract

This paper asks which observable content and search signals are associated with pages receiving AI referral traffic, and whether that association can be turned into a ranked review list for a content team. Using FlyRank's pseudonymized search warehouse for a mid-panel month, I built a small feature set from Google Search Console and GA4 signals and compared a simple impression-threshold baseline against a logistic regression ranking model. The model produced a modest but real improvement over the baseline, while a deliberate leakage test confirmed the gain was not an artifact of circular features. Because AI-referral sessions are sparse, the result is best read as a directional, decision-support ranking rather than a confident predictive model — a starting point for human review, not a guarantee of AI visibility gains.

01Introduction

AI-powered search tools increasingly send referral traffic to content that they judge worth citing, quoting, or summarizing. Content teams currently have almost no visibility into which of their pages already earn some of this traffic, or which under-performing pages might be easy wins if restructured. This work supports a specific decision: given limited review capacity, which pages should a content or SEO team look at first when trying to improve AI visibility? The output is not a guarantee that any specific page will gain AI traffic — it is a ranked shortlist that replaces guesswork with an evidence-based starting point.

02Data

This analysis uses FlyRank's pseudonymized internship warehouse release (flyrank_pseudonymized_warehouse_release_v20260703), accessed via the gated Hugging Face dataset FlyRank/internship-warehouse. The primary table is fact_content_daily_performance, a daily fact table keyed by client, content item, and report date.

Development and validation were performed on a single mid-panel month, month=2026-03, deliberately avoiding the dataset's final sealed month (which is reserved as an unseen test window for future-looking labels and was not used here). The raw slice for this month contains 9,841,378 daily fact rows spanning 2026-03-01 through 2026-03-31. After removing rows with missing values in the modeling columns, 2,082,695 rows remained for analysis.

Excluded from this work, and why:

  • Raw client names, domains, URLs, titles, and queries — never present in the release; all identifiers are pseudonymized hash IDs used only for joining and grouping.
  • FlyRank's own product-computed fields (health_score, priority_score, action_type) — excluded to avoid a circular result, where a model simply learns to reproduce an existing rule instead of discovering signal from raw data.

03Methodology

Because only a small fraction of content items in the warehouse show any AI-referral sessions, this problem was framed as a scoring / ranking task, not binary classification. Training a classifier on such a rare positive class risks a model that looks accurate on paper while being practically unreliable.

Label / proxy: sessions_ai > 0, used to validate whether a ranking of pages by predicted score correlates with observed AI referral activity — not treated as a confident ground truth. In this month's data, only 0.23% of rows carry a positive label — direct confirmation that AI referral activity is extremely sparse, and a key reason this is framed as ranking rather than classification.

Features (all observable independent of the outcome being ranked):

  • gsc_impressions — Search Console impressions, logged daily.
  • gsc_avg_position — average search ranking position.
  • ga4_sessions — total analytics sessions.
  • ga4_engaged_sessions — sessions with meaningful engagement.

Baseline: a single-rule flag — pages with gsc_impressions above the month's median are marked as opportunities.

Models compared: Logistic Regression (interpretable, probability-based ranking) and Random Forest (to test whether a more flexible, non-linear method meaningfully improves ranking quality).

Split design: the primary comparison uses a random 70/30 train/test split. Because the data is at a content-item-per-day grain, the same page can appear on multiple days, so a purely random split risks letting the model see a page's pattern in training and again in testing. To check this, the honest logistic regression result was re-run under a grouped split — grouped by content_hash_id, so no single page's rows can appear in both the train and test sets.

Leakage audit: as a deliberate test in an earlier notebook, sessions_ai itself (the source of the label) was added as a feature. The score jumped sharply toward a perfect result, confirming leakage — this column was removed and excluded from every model reported below. The final feature set was re-checked to confirm it contains no FlyRank product-computed fields (health_score, priority_score, action_type) and no direct copy of the label.

04Results

The table below compares the baseline rule against two models on the same random 70/30 test split, using ROC AUC.

MethodROC AUC
Baseline (impressions > median)0.697
Logistic regression0.782
Random forest0.948

Both models clear the fixed-threshold baseline by a wide margin. The random forest's high score (0.948) is notable, but should be read cautiously: with a rare positive class and a content-item-per-day grain, a flexible model can partly pick up page-specific patterns rather than generalizable signal — this is examined directly below.

Honest validation — grouped split. Because the same content page can appear on multiple days in this dataset, a random split risks letting the model see a page in both training and testing. Re-running the logistic regression under a split grouped by content_hash_id (so a page's rows can never appear in both sets) gives a direct before/after comparison:

Split designROC AUC (Logistic Regression)
Random split (before)0.7818
Grouped by content page (after)0.7834

The two scores are nearly identical, which is a reassuring result: it suggests the logistic regression's performance was not meaningfully inflated by page repetition across days, and the model is picking up genuine signal rather than memorizing individual pages.

Fig. 1 — Reason-code distribution across 2,082,695 scored page-days, month=2026-03.

What the model leans on. Random forest feature importances place ga4_sessions highest (0.354), followed by gsc_avg_position (0.288), gsc_impressions (0.265), and ga4_engaged_sessions (0.093) lowest. This suggests overall session volume and ranking position carry more separating power than raw impression counts or engaged-session counts alone.

Error analysis. On this test split, the random forest produced zero confident false positives (cases where it predicted >50% probability of AI traffic but the page had none). Combined with the extremely rare positive rate (0.23%), this indicates the model is being conservative rather than over-flagging — consistent with a sparse-signal setting where the model has learned to reserve high-confidence scores for a small number of genuinely strong candidates.

05Limitations & Honest Framing

What this work can say

Certain observable content and search signals are associated with pages that already receive AI referral sessions, and a simple model can rank pages by this association better than a fixed threshold rule.

What this work cannot say

  • It cannot claim that editing a page will cause AI referral traffic to increase — that requires a controlled experiment, not observational data.
  • It cannot describe or predict how any specific AI platform's citation or ranking logic works.
  • Results are validated on a single month and a single unbalanced client panel; they may not generalize across time or across clients with less tracking history.
  • AI-referral sessions are sparse enough that any single ranking should be treated as directional, not a confident forecast.

Intended use, human review, and no-go cases

Intended for: a content strategist or SEO manager with limited review time, deciding which pages to look at first. Stops being valid outside month=2026-03 without re-validation, or if treated as a guarantee rather than a hypothesis.

Before acting, a human should check: whether the page's topic is still relevant to the business; whether the recommended change fits the page's actual content type; and whether traffic/engagement figures reflect a one-off spike rather than sustained behavior.

Should never be automated: automatically rewriting or publishing content changes, deleting or pruning pages, or presenting the opportunity score as a public-facing claim about a page's quality. This playbook only prioritizes review.

Monitoring and retrain triggers

Signals that this playbook has gone stale: the data month drifting far from current traffic patterns; a significant change in site content mix; new tracking gaps (e.g. GA4 availability dropping for previously-tracked pages); or a drop in the grouped-split AUC on a freshly validated month. Recommended trigger: re-run the scoring pipeline monthly, or immediately after any major site or tracking change, and re-check the honest AUC before trusting a new ranked queue.

06Ranked Recommendations

Each page-day in the scored dataset receives a reason code based on where it sits on visibility and engagement, mapped directly to a suggested action:

Reason codeCountSuggested action
visible_engaged_page21,134Review for AI structure
high_visibility_low_engagement690,420Improve engagement, then review
high_engagement_low_visibility3,975Monitor
low_priority1,367,166No action

The top tier — visible_engaged_page — represents the clearest starting point: pages with both strong search visibility and strong engagement, sharing a profile with pages that already show AI referral activity elsewhere in the dataset. Recommended actions for this tier: add clear, self-contained definitions or FAQ-style blocks near the top of the page, and strengthen explicit source attribution, since these structural traits are believed to make a page easier for AI systems to cite. This is a prioritized starting point for human review, not a guarantee of AI traffic gain.

One practical caveat surfaced during review: the same content page can appear many times in a day-level ranked list, since the underlying grain is content-item-per-day. A team using this queue in practice should first aggregate to one row per page (e.g., by taking the max or mean score across the month) so the reviewed list reflects distinct pages rather than one strong page's repeated daily entries.
